# ADR-001：Modular Monolith（模块化单体）

## 状态

Accepted

## 日期

2026-09-22

## Context

项目定位为"智能广播设备管理与运维平台"。在架构决策阶段面临以下约束：

- 业务领域（广播设备管理）处于起步阶段，业务规模和边界尚不完全明确
- 团队需要快速迭代和验证，AI Coding 需要在清晰结构中高效工作
- 未来可能存在 AI Agent、设备通信协议、后台任务等需求，但当前无法确定其规模和频率
- 过早拆分微服务会引入分布式系统复杂性（网络延迟、数据一致性、服务发现、运维成本），而当前业务规模不需要这些能力
- 项目需要在单一代码库中完成从需求到部署的完整 AI Coding 工作流

## Decision

第一阶段采用 **Modular Monolith（模块化单体）** 架构：

1. 整个后端运行在单一进程中，不拆分微服务
2. **业务模块是一级组织单位**（`internal/modules/<module>/`），模块内部进行领域分层
3. 模块间通过 Application 层定义的接口交互，禁止直接访问其他模块的 Infrastructure 层或 domain 层
4. 应用级基础设施放在 `internal/platform/`（配置、数据库、日志等）；跨模块共享的类型和契约遵循 Shared Kernel 约束（详见下文）
5. 每个模块具备独立可测试性（可在不启动其他模块的情况下进行单元测试）
6. 只有当以下**全部**条件满足时，才考虑将模块拆分为独立进程：
   - 模块存在明确的独立部署需求（如独立扩缩容、独立发布节奏）
   - 模块的技术约束不适合在单体内运行（如实时通信、长时间阻塞任务）
   - 拆分后的运维成本可控且团队具备相应能力

### 目录结构

``text
internal/
├── modules/
│   └── <module>/
│       ├── domain/          # 领域模型、业务规则、错误定义
│       ├── application/     # 应用服务、用例编排、对外接口契约
│       ├── interfaces/      # HTTP handler、请求/响应 DTO、路由注册
│       └── infrastructure/  # 持久化实现、外部服务适配
└── platform/                # 应用内部基础设施（config/database/logging/errors/response）
``

### 依赖方向

``text
interfaces/  →  application/  →  domain/
infrastructure/  →  application/  →  domain/
模块 A 的 application/ ←→ 模块 B 的 application/（通过接口契约）
``

### 模块间通信规则

- 模块 A 通过模块 B 的 Application 层接口调用模块 B 的能力
- 禁止模块 A 直接 import 模块 B 的 `domain/` 包
- 禁止模块 A 直接访问模块 B 的 `infrastructure/` 包
- 禁止模块间循环依赖（如 A→B→A）

### Shared Kernel 约束

Shared Kernel 是各模块 `application/` 层共享的接口和类型定义，不是独立的包或目录。

- 只能存放真正跨模块共享且**稳定**的类型和契约（如设备 ID 类型、通用枚举、跨模块事件契约）
- 不允许承载业务逻辑（业务逻辑属于具体模块的 `domain/`）
- 变更 Shared Kernel 类型必须评估对所有消费模块的影响
- Shared Kernel 类型可放在发起方模块的 `application/` 层，也可提取到 `internal/platform/types/`，但必须严格控制变更频率

### internal/platform/ 职责

`internal/platform/` 提供与业务无关的应用级基础设施：

| 子包 | 职责 |
|------|------|
| `config/` | 配置加载与环境管理 |
| `database/` | 数据库连接、迁移、健康检查 |
| `logging/` | 结构化日志 |
| `errors/` | 标准错误定义与映射 |
| `response/` | 统一 API 响应结构 |
| `metrics/` | 指标采集（预留） |
| `cache/` | 缓存抽象（预留，仅在 ADR 评估后实现） |

依赖方向：`modules/` → `platform/`（模块依赖平台，平台不依赖模块）。

根目录 `pkg/` 第一阶段不创建；只有当确实存在需要被外部 Go 项目 import 的公共库时才启用。

## Alternatives Considered

### 1. 从第一天开始微服务架构

- **优势**：天然支持独立部署和扩缩容
- **劣势**：引入分布式系统复杂性（网络、一致性、服务发现、链路追踪），开发效率低，AI Coding 需要跨多个仓库工作，当前业务规模不需要
- **否决原因**：过早优化，当前阶段没有需要独立部署的业务模块

### 2. 传统分层单体（Controller → Service → Repository），不按业务模块组织

- **优势**：结构简单，小项目友好
- **劣势**：业务维度与技术维度混杂，随模块增加导致 `service/` `repository/` 膨胀，模块边界模糊
- **否决原因**：不利于模块隔离和 AI Coding 的上下文管理

### 3. Hexagonal Architecture（六边形架构）严格应用

- **优势**：依赖反转彻底，测试友好
- **劣势**：对小模块过度设计，增加理解成本，目录层级过多
- **否决原因**：本项目采用模块化单体内每个模块按需分层的方式，既保留六边形的核心思想（依赖方向向内），又不强制每个模块都完整实现所有端口和适配器

## Consequences

### 正面

- 单一可部署产物，运维成本低，部署流程简单
- AI Coding 可以在一个代码库中完成完整工作流
- 模块边界清晰，便于理解和维护
- 模块可独立测试，测试速度快
- 未来可按需拆分（模块已经具备独立边界）

### 负面

- 需要纪律性维护模块边界，防止模块间隐式耦合
- 所有模块共享同一进程，某个模块的 bug 可能影响整个系统
- 单体编译时间随模块增长而增加
- 模块间通信走进程内调用，无法像微服务那样做熔断隔离

### 维护模块边界的手段

- Code Review 检查跨模块 import 是否合规
- 未来可引入 Go 的 `go vet` 自定义规则或 `depguard` 检查包级依赖
- Integration Test 验证模块间契约

## Revisit Conditions

以下情况触发重新评估本决策：

1. **独立扩缩容需求**：某个模块的流量模式与其他模块显著不同，需要独立扩缩容
2. **独立发布需求**：某个模块的发布节奏与其他模块不兼容，频繁发布影响系统稳定性
3. **技术约束**：某个模块需要使用不同的运行时或语言（如 AI Agent 需要 Python）
4. **团队规模**：团队增长到需要按模块分配独立开发小组，且模块间协调成本过高
5. **故障隔离需求**：某个模块的故障频繁影响整个系统可用性
6. **合规要求**：某个模块的数据或处理需要物理隔离

## 验证方式

- 确认 `internal/modules/` 下每个模块目录可独立进行 `go test`
- 确认不存在模块 A 的 `domain/` 直接 import 模块 B 的 `infrastructure/` 的情况
- 确认不存在模块间循环依赖
