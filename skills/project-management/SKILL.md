# Skill：project-management

## 名称

project-management

## 描述

负责本项目的需求分析、范围控制、任务拆解、实现计划制定和任务状态跟踪。

## 适用场景

- 引入新的需求、功能或变更请求。
- 现有需求需要澄清或补充验收标准。
- 工作需要拆分为可实现的任务。
- 范围发生变化，或任务存在超出批准范围的风险。
- 需要向 Human 汇报任务状态。

## 输入

- 产品需求或用户请求。
- `docs/product/`、`docs/architecture/`、`docs/modules/`、`docs/decisions/` 下的相关文档。
- 当前仓库状态。
- 已知约束、截止时间和验收标准。

## 前置条件

- 请求目标已经清晰到可以分析。
- 已阅读现有相关文档。
- 不通过臆造业务行为来填补缺失需求。

## 执行步骤

1. 用与实现无关的语言重述请求目标。
2. 识别范围内、范围外、假设、依赖和待确认问题。
3. 将需求转化为可验证的验收标准。
4. 判断是否需要架构决策。
5. 将已批准工作拆分为小任务，并为每个任务定义预期产出和验证方式。
6. 标记风险、顺序约束和回滚考虑。
7. 保持实现计划与文档一致，并在获得批准后更新文档。

## 检查项

- 每个任务都能映射到需求或已批准的技术需要。
- 验收标准可观察、可测试。
- 未经批准，不引入框架、数据库、服务或业务模块。
- 范围变化被明确标出。

## 输出

- 需求分析摘要。
- 实现计划。
- 包含验证步骤的任务列表。
- 待确认问题和所需决策。
- 在请求或批准后的文档更新。

## Definition of Done

- 范围清晰。
- 验收标准可测试。
- 任务足够小，便于实现和审查。
- 已识别需要 Human 决策的事项。
- 未引入隐藏的业务或技术假设。

## 失败处理

- 如果需求存在歧义，产出最小有用分析，并列出阻塞问题。
- 如果任务与现有文档或 ADR 冲突，停止并报告冲突。
- 如果实现过程中范围扩大，暂停并请求确认。

## 必须停止并询问用户的情况

- 无法在不选择业务行为的情况下推导验收标准。
- 需要做出技术或架构决策。
- 请求与已接受的 ADR 冲突。
- 变更会在未批准的情况下创建新业务模块或公开契约。
